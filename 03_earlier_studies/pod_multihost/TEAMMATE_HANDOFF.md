# Help needed: one 3-machine Spark run for a research paper

**What this is.** This package measures "ground truth" for a paper
about predicting distributed-pipeline failures: the same 9 data
pipelines are executed once on a real multi-machine Spark cluster, and
their true per-partition loads are read from Spark's event log. A
previous run did this on a single machine with 2 worker processes;
reviewers (correctly) asked for the real thing — separate hosts, real
network shuffle. Your 3 machines would close that gap. Nothing about
the data is private: the dataset is synthetic, generated by the
package itself from a fixed seed.

**What to run.** Full instructions: **HOSTS_RUNBOOK.md** (in this
package). The short version — unpack the package at the same path on
all 3 hosts, fill in `cluster.env` (host addresses + your Python ≥3.12
venv; the template explains every field), open the six ports listed in
the runbook between the hosts, then:

```bash
# Host A:        bash setup_multihost.sh        # master
# Host B:        bash setup_multihost.sh        # worker
# Host C:        bash setup_multihost.sh        # worker
# Host A:        bash run_master.sh             # generates data, runs, collects
# Hosts B and C: bash run_worker.sh --archive   # gathers worker logs
```

**Expected wall time (estimate).** About **30–45 minutes total**,
including installs: JDK + Spark download and cluster bring-up ~10
minutes, dataset generation seconds, the 9 pipelines under a minute of
execution plus a few minutes of Spark start/stop overhead, collection
under a minute. Allow an hour to be safe. (Estimate extrapolated from
the instrumented single-host run; first-time setup friction is the
wildcard.)

**Hard rules — please don't improvise around these:**

1. **Do not change the verdict threshold (T = 200,000), the pipeline
   definitions, or the generator's seed/sizes.** Comparability with
   the existing study is the entire point.
2. **numpy must be exactly 2.5.4** and the interpreter ≥ Python 3.12 —
   the scripts check this and the generator has a SHA-256 check that
   fails the run if the data isn't bit-identical to the reference.
   If it fails, it's the environment, not the check: fix the
   environment, never the check.
3. **F_A and F_B reporting `SKIPPED_NOT_MATERIALISABLE` is expected**,
   not an error — their full join outputs are hundreds of billions of
   rows; the package computes their loads analytically from real Spark
   counts instead, by design.
4. **If cross-host shuffle or worker registration fails, do not work
   around it** by running everything on one host and sending that back
   as the result. Send the logs back instead (checklist below) — a
   precise failure report is valuable; a silently downgraded run is
   worse than none.
